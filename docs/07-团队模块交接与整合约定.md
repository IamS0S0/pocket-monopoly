## 已存在的接口

| 接口 | 输入 | 输出与约束 |
| --- | --- | --- |
| `createDefaultConfig()` | 无 | 新配置，默认都市、2 人、30 回合 |
| `validateConfig(config)` | 完整配置 | 合法返回 true，不合法抛中文 Error |
| `setPlayerCount(config, count)` | 有效配置、2/3/4 | 新配置；保留剩余座位，补充未占用角色 |
| `selectCharacter(config, index, id)` | 有效配置、玩家索引、角色标识 | 新配置，必要时交换角色 |
| `createGameState(config)` | 完整配置 | 校验后创建独立初始状态 |
| `mountMenu(root, callbacks)` | DOM 容器及 onPreview/onStart | 建立大厅；目前 onStart 必须返回状态供摘要使用 |
| `WorldPreview.update(map, players)` | 主题对象、玩家数组 | 更新大厅微缩预览 |
| `WorldPreview.dispose()` | 无 | 停止循环、释放资源、移除画布 |

`setPlayerCount` 和 `selectCharacter` 接收的是已有有效配置，不能替代对任意外部数据的完整校验。

## 下一阶段需要共同修改的位置

当前 `menu.js` 在 onStart 返回后会立即展示摘要。接入真实棋盘时，要同时修改该启动分支与 `main.js`，不要只在 onStart 回调中替换页面后，仍让旧菜单访问被移除的元素。

当前菜单事件绑定在 root 上，重新挂载前需要增加清理机制，或使用新的页面容器。否则反复返回大厅可能累积事件监听。当前版本只挂载一次，不包含对局返回大厅功能；这一生命周期改造属于下一阶段接入工作。

## 规则与表现的边界

- core 层只使用普通 JavaScript，不导入 Three.js、document 或 window。
- 规则引擎决定点数、位置、金币与回合；渲染层展示已确定的结果。
- AI 产生候选动作，由规则引擎确认是否合法，不能直接修改金币或回合。
- UI 展示状态并提交意图，不自行决定获胜者或资产变化。
- 后续异步移动、掷骰和退场需有取消机制，旧对局回调不得影响新局。

这些是后续实现约定，不代表相关引擎和取消机制已经完成。

## 整合验收顺序

1. 查看本次实际修改文件与提交说明，明确是否变更接口。
2. 运行 `npm ci`（新电脑或锁文件变化时）、`npm test`、`npm run build`。
3. 运行 `npm run dev`，检查已有大厅功能是否退化。
4. 按新增模块的验收清单操作；记录发现的问题与修复。
5. 更新 README 的功能对照表、阶段状态和测试报告。
6. 完成本阶段交接并暂停；确认后进入下一阶段。
